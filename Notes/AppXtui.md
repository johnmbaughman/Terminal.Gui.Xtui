# App.xtui / App.xaml Pattern for Terminal.Gui (Generator-only)

Goal

- Provide a lightweight, generator-only pattern that lets a developer author an `App.xtui` (or `App.xaml`) to declare application-level resources (converters, brushes, styles), a `StartupUri`, and optional global settings.
- The generator must emit code into the user's assembly; it must not add a runtime dependency on `Terminal.Gui.Xtui`.
- The generated code will provide a concise API for resolving application-level resources at runtime and optionally generate a `Program.Main` entry point if the project lacks one.

Overview of approach

- The generator parses `App.xtui` as an additional file and builds a small model: resources, StartupUri, merged dictionaries, and any compile-time-resolvable types (converter types etc.).
- For resources the generator can fully resolve, it emits private static cached instances and registers them into an application-level resource store inside the generated file.
- All generated helpers and bootstrap code are compiled into the user's assembly; they reference only BCL and the existing `Terminal.Gui` runtime assembly.
- Views and other generated `.Xtui.g.cs` files look up application resources via the helper API (no runtime Xtui dependency required).

Example `App.xtui` (input)

```xml
<Application xmlns="http://schemas.microsoft.com/winfx/2006/xaml"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             xmlns:conv="clr-namespace:MyApp.Converters"
             x:Class="MyApp.App">
  <Application.Resources>
    <conv:BoolToTextConverter x:Key="BoolToText" />
    <conv:ColorToBrushConverter x:Key="ColorToBrush" />
  </Application.Resources>

  <!-- Optional: initial window to show at startup when no Program.Main exists -->
  <Application.StartupUri>Views/MainWindow.xtui</Application.StartupUri>
</Application>
```

What the generator will produce (high-level)

- A generated file `AppXtui.g.cs` compiled into the user's assembly that contains:
  - A small `__Xtui_AppHelpers` type exposing `RegisterResource`, `TryGetResource`, and `EnsureInitialized`.
  - Private static cached resource fields for resolvable resources.
  - A module initializer or an `EnsureInitialized()` method that registers cached resources into the app store.
  - Optionally, a `Program.Main` if no entry point exists and generator was allowed to supply one (configurable).

Detailed generated example: `AppXtui.g.cs`

using System;
using System.Collections.Generic;
using System.Runtime.CompilerServices;
using Terminal.Gui.ViewBase; // runtime assembly types known to the user's project

namespace MyApp
{
    internal static class __Xtui_AppHelpers
    {
        // Application-level resource store (private to generated code)
        private static readonly Dictionary<string, object> s_resources = new(StringComparer.Ordinal);
        private static bool s_initialized = false;

        public static void RegisterResource(string key, object value) => s_resources[key] = value;

        public static bool TryGetResource(string key, out object? value) => s_resources.TryGetValue(key, out value);

        public static IReadOnlyDictionary<string, object> Resources => s_resources;

        public static void EnsureInitialized()

        internal static readonly MyApp.Converters.ColorToBrushConverter _res_ColorToBrush = new MyApp.Converters.ColorToBrushConverter();
    }

        ## EnsureInitialized Approach

        Instead of relying on module initializers, the generator should use an explicit, idempotent `EnsureInitialized()` method emitted into the user's assembly. This approach puts initialization under the application's control, avoids early execution surprises, and is compatible with older toolchains.

        Why prefer `EnsureInitialized()`

        - Explicit call sites: `EnsureInitialized()` is invoked from a known location (the user's `Main` or a generated `Program.Main`) so initialization ordering and thread context are controlled.
        - Safer for Terminal.Gui: the framework performs driver selection and thread creation in `Application.Init()`, which must run at a controlled point in startup; `EnsureInitialized()` allows the generator to register resources before `Application.Init()` without starting drivers or threads.
        - Backwards compatible: works on older compilers and TFMs where module initializers are unavailable.

        Practical generator pattern

        - Emit a small helper type into the generated `AppXtui.g.cs` with the following responsibilities:
          - hold `RegisterResource` / `TryGetResource` and an idempotent `EnsureInitialized()` method,
          - optionally register compile-time cached resource instances inside `EnsureInitialized()` (or a separate registrar called by it),
          - expose a no-op-friendly API so views can call `__Xtui_AppHelpers.EnsureInitialized()` safely before looking up resources.

        Idempotent `EnsureInitialized()` example

        ```csharp
        internal static class __Xtui_AppHelpers
        {
            private static volatile bool s_initialized;
            private static readonly object s_lock = new object();

            public static void EnsureInitialized()
            {
                if (s_initialized) return;
                lock (s_lock)
                {
                    if (s_initialized) return;
                    s_initialized = true;

                    // register compile-time-resolved resources
                    RegisterResource("BoolToText", new MyApp.Converters.BoolToTextConverter());
                    RegisterResource("ColorToBrush", new MyApp.Converters.ColorToBrushConverter());
                }
            }

            public static void RegisterResource(string key, object value) { /* store in private dictionary */ }
            public static bool TryGetResource(string key, out object? value) { /* lookup from private dictionary */ }
        }
        ```

        Generator-emitted `Program.Main` example (only when no user `Main` exists)

        ```csharp
        public static class Program
        {
            public static void Main()
            {
                __Xtui_AppHelpers.EnsureInitialized();
                Application.Init();
                var window = new MyApp.Views.MainWindow();
                Application.Run(window);
            }
        }
        ```

        How views should use it

        - Generated views should call `__Xtui_AppHelpers.EnsureInitialized()` before attempting to resolve application resources. Because the method is idempotent and cheap after the first call, this is safe to do from multiple generated files.

        Example usage in a generated view

        ```csharp
        __Xtui_AppHelpers.EnsureInitialized();
        if (__Xtui_AppHelpers.TryGetResource("BoolToText", out var __r) && __r is IValueConverter conv)
            binding.Converter = conv;
        ```

        Compatibility guidance

        - If the generator targets older compilers, prefer `EnsureInitialized()` over module initializers; the generator can emit the same registration logic into `EnsureInitialized()` and instruct (or generate) a `Main` that calls it.
        - Keep `EnsureInitialized()` minimal and avoid long-running or blocking operations; registration should be fast and deterministic.

        Recommendations summary

        - Use `EnsureInitialized()` as the primary initialization mechanism.
        - Generate a `Program.Main` only when the compilation has no entry point; call `EnsureInitialized()` there before `Application.Init()`.
        - Avoid calling `Application.Init()` from any generated automatic initializer; keep control of driver and thread startup explicit in `Main`.

    // Parse the App.xtui into a lightweight model
    private static AppModel ParseAppModel(string xml, string path)
    {
        var doc = XDocument.Parse(xml);
        var root = doc.Root!;
        var model = new AppModel { FilePath = path };

        // StartupUri
        var startup = root.Elements().FirstOrDefault(e => e.Name.LocalName == "StartupUri");
        if (startup != null) model.StartupUri = startup.Value.Trim();

        // Resources: look for immediate child Application.Resources and collect elements with x:Key
        var resParent = root.Elements().FirstOrDefault(e => e.Name.LocalName.EndsWith("Resources"));
        if (resParent != null)
        {
            foreach (var elem in resParent.Elements())
            {
                var keyAttr = elem.Attributes().FirstOrDefault(a => a.Name.LocalName == "Key" || a.Name.LocalName == "x:Key");
                if (keyAttr != null)
                {
                    model.Resources.Add(new AppResource { Key = keyAttr.Value, ElementName = elem.Name.LocalName, Raw = elem });
                }
            }
        }

        return model;
    }

    // Resolve resource types using Compilation
    private static List<ResolvedResource> ResolveResourceTypes(Compilation compilation, AppModel model)
    {
        var results = new List<ResolvedResource>();
        foreach (var r in model.Resources)
        {
            // Try to map XML element name to type symbol. Generator must understand xml namespaces mapping; for the sketch
            // we attempt short-name lookup by scanning types.
            var typeSym = FindTypeByShortName(compilation, r.ElementName);
            if (typeSym != null)
            {
                results.Add(new ResolvedResource { Key = r.Key, TypeSymbol = typeSym });
            }
        }
        return results;
    }

    // Example helper: search for types with short name in the compilation
    private static ITypeSymbol? FindTypeByShortName(Compilation compilation, string shortName)
    {
        // naive scan: traverse global namespace
        var matches = new List<ITypeSymbol>();
        CollectTypesByName(compilation.GlobalNamespace, shortName, matches);
        return matches.FirstOrDefault();
    }

    private static void CollectTypesByName(INamespaceSymbol ns, string shortName, List<ITypeSymbol> outList)
    {
        foreach (var t in ns.GetTypeMembers())
        {
            if (t.Name == shortName) outList.Add(t);
        }
        foreach (var sub in ns.GetNamespaceMembers()) CollectTypesByName(sub, shortName, outList);
    }

    // Resolve StartupUri -> Type symbol using x:Class mapping
    private static INamedTypeSymbol? ResolveStartupType(Compilation compilation, string? startupUri)
    {
        if (string.IsNullOrEmpty(startupUri)) return null;
        // If startupUri is an xtui path, attempt to map to x:Class in that xtui file (not shown here)
        // For sketch assume startupUri is a type name
        return compilation.GetTypeByMetadataName(startupUri);
    }

    // Generate the AppXtui.g.cs source text
    private static string GenerateAppSource(AppModel model, List<ResolvedResource> resolvedResources, INamedTypeSymbol? startupType, bool hasEntryPoint)
    {
        var sb = new StringBuilder();
        sb.AppendLine("// <auto-generated />");
        sb.AppendLine("using System;\nusing System.Collections.Generic;\nusing Terminal.Gui.ViewBase;\n");
        sb.AppendLine("namespace " + (GetRootNamespace(model) ?? "") + "\n{");
        sb.AppendLine("    internal static class __Xtui_AppHelpers\n    {\n        private static readonly Dictionary<string, object> s_resources = new(StringComparer.Ordinal);\n        private static bool s_initialized = false;\n\n        public static void RegisterResource(string key, object value) => s_resources[key] = value;\n        public static bool TryGetResource(string key, out object? value) => s_resources.TryGetValue(key, out value);\n        public static void EnsureInitialized() { if (s_initialized) return; s_initialized = true; /* registration follows */ }");
        sb.AppendLine("    }\n");

        // emit cached resources class
        sb.AppendLine("    internal static class __Xtui_AppResources\n    {\n");
        foreach (var rr in resolvedResources)
        {
            var fqName = rr.TypeSymbol!.ToDisplayString();
            sb.AppendLine($"        internal static readonly {fqName} _res_{Sanitize(rr.Key)} = new {fqName}();");
        }
        sb.AppendLine("    }\n");

        // now finish EnsureInitialized with registration calls
        sb.AppendLine("    internal static partial class __Xtui_AppHelpers_Registrar\n    {\n        public static void __RegisterAll()\n        {\n");
        foreach (var rr in resolvedResources)
        {
            sb.AppendLine($"            __Xtui_AppHelpers.RegisterResource(\"{rr.Key}\", __Xtui_AppResources._res_{Sanitize(rr.Key)});\n");
        }
        sb.AppendLine("        }\n    }\n");

        // optional Program.Main emission is omitted here for brevity; generator will only emit it if hasEntryPoint == false

        sb.AppendLine("}");
        return sb.ToString();
    }

    private static string GetRootNamespace(AppModel model) => "MyApp"; // placeholder; the generator should infer from x:Class or project

    private static string Sanitize(string key) => key.Replace('-', '_').Replace(' ', '_');

    // Model types for the sketch
    private class AppModel { public string FilePath = ""; public string? StartupUri; public List<AppResource> Resources = new(); }
    private class AppResource { public string Key = ""; public string ElementName = ""; public XElement? Raw; }
    private class ResolvedResource { public string Key = ""; public ITypeSymbol? TypeSymbol; }
}

Generator emission policies / diagnostics

- If a resource type cannot be resolved or doesn't implement the expected interface (e.g., `IValueConverter`), emit a compiler diagnostic explaining what failed and where.
- If generator decides not to emit `Program.Main` because the project already has an entry point, include `EnsureInitialized()` and a short comment instructing developers to call it early in startup.
- If generator emits `Program.Main`, keep it minimal and safe: call `EnsureInitialized()` then `Application.Init()` then `Application.Run(new StartupType())`.

Edge cases and recommendations

- Threading: avoid calling `Application.Init()` automatically from module initializers; prefer explicit `Program.Main` generation or `EnsureInitialized()` method the user's code can call.
- Resource identity: generated cached resources live in generated fields. If you rely heavily on resource identity (reference equality), document how generated caching works vs runtime-loaded merged dictionaries.
- Merged dictionaries or theme swaps: those are runtime concerns; generator should provide lookup helpers but not attempt to reason about runtime-loaded dictionaries across assemblies.

Conclusion / suggested next steps

- Implement the `IIncrementalGenerator` sketch into your generator project and test with a small sample app that contains `App.xtui` and a `MainWindow.xtui`.
- Start simple: emit `__Xtui_AppHelpers` and `EnsureInitialized()` first, then add cached resource emission and `Program.Main` generation later.
- Keep generated code self-contained inside the user's assembly to avoid runtime `Terminal.Gui.Xtui` dependencies.

## ModuleInitializer vs EnsureInitialized Discussion

### Module Initializer Approach
Module initializers are a C# compiler feature that lets you mark a static, parameterless method to be run once when the module (assembly) is loaded. The attribute is `System.Runtime.CompilerServices.ModuleInitializerAttribute`. When present, the compiler arranges for the method to be executed by the runtime automatically; you do not need to call it explicitly.

Concrete example — simple module initializer

```csharp
using System.Runtime.CompilerServices;

internal static class StartupHelpers
{
    [ModuleInitializer]
    internal static void Init()
    {
        // runs once when the assembly/module is loaded
        // keep this minimal and robust
    }
}
```

Important characteristics

- Requirements: the method must be `static`, parameterless, `void`, and non-generic.
- Timing: runs when the CLR loads the module — effectively before most other code in that assembly executes.
- Ordering: there is no guaranteed order across assemblies; multiple initializers in the same assembly run in a compiler-chosen order but do not have a reliable cross-assembly ordering.
- Failure handling: an exception that propagates out of a module initializer will fail module load; always catch and handle exceptions inside the initializer.

When module initializers are appropriate for a generator

- Good: registering small, deterministic, compile-time-known data (e.g., constructing and registering converter instances or other immutable resources) into an in-assembly store. These actions don't require UI-thread affinity or heavy runtime context.
- Not good: anything that must run on the UI thread or requires the app to be in a particular state (for example, calling `Application.Init()` for a GUI framework). Also avoid long-running I/O or network calls.

Practical generator pattern

- Emit a tiny helper in the user's assembly (the generated `.g.cs`) that exposes `EnsureInitialized()`, `RegisterResource(...)`, and `TryGetResource(...)`.
- Put only safe registrations inside a module initializer. Keep high-level initialization (UI init, theme application, merged-dictionary merging) inside `EnsureInitialized()` which the generated `Program.Main` (if emitted) or the user's `Main` will call explicitly.

Safe generated example

```csharp
internal static class __Xtui_AppHelpers
{
    private static bool s_initialized;

    public static void EnsureInitialized()
    {
        if (s_initialized) return;
        s_initialized = true;
        // any work that must run on app startup thread
    }

    [System.Runtime.CompilerServices.ModuleInitializer]
    private static void __ModuleInit()
    {
        try
        {
            // safe, deterministic registrations only
            RegisterResource("BoolToText", new MyApp.Converters.BoolToTextConverter());
        }
        catch
        {
            // swallow to avoid breaking module load
        }
    }

    public static void RegisterResource(string key, object value) { /*...*/ }
    public static bool TryGetResource(string key, out object? value) { /*...*/ }
}
```

Example: generating `Program.Main` that calls `EnsureInitialized()`

If the generator determines there is no project entry point it may emit a small `Program.Main` that calls `EnsureInitialized()` and then performs normal startup (call `Application.Init()` and `Application.Run(...)`). This approach keeps explicit UI initialization under the project's control while still making resource registration automatic.

```csharp
public static class Program
{
    public static void Main()
    {
        __Xtui_AppHelpers.EnsureInitialized();
        Application.Init();
        var window = new MyApp.Views.MainWindow();
        Application.Run(window);
    }
}
```

Compatibility and fallback

- Module initializers require compiler and runtime support (C# 9+ / .NET 5+ toolchains typically). If the generator targets older frameworks or compilers that don't support module initializers, emit the same registrations inside `EnsureInitialized()` and document that the app or generated `Main` must call it.
- You may also emit a small internal polyfill attribute type when targeting older frameworks, but defining the attribute alone does not create module initializer behavior unless the compiler recognizes and wires it; the attribute polyfill is not a substitute for compiler support.

Recommendations

- Use module initializers sparingly and only for small, safe registrations.
- Rely on `EnsureInitialized()` for anything that is ordering- or thread-sensitive; call it explicitly from generated `Main` or from user `Main` early in startup.
- Always catch exceptions inside module initializers and make initialization idempotent.
